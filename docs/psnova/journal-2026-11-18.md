# Journal 2026-11-18: Phantasy Star Nova from a dump to New Game in one day

The journey, in order, with what worked, what didn't, and why. The state of things is in [README.md](README.md); this
file is the story behind it, so the next session doesn't repeat the detours. Every claim says how it was checked.

## 0. Starting point and choices

- The dump (`F:\RECOMP GAMES\Phantasy Star Nova (v1.05)`) is a raw Vita copy: `app` (encrypted PFS, NoNpDrm
  `work.bin`), `patch` (1.05), `rePatch` (the Arks-Layer English fan translation: two CPK archives).
- **Base: Project Nativ**, already working for Uncharted in `..\recent recomps\Uncharted Golden Abyss Recomp`. A Vita
  game there is a pack (`packs/<title>/pack.toml`), not a new recompiler (retrospective lesson: use the existing tool).
- **Isolation**: a git worktree of that checkout on branch `psnova` from `main` (not from the RT branch: main is clean
  Nativ + Windows fixes; RT carries Uncharted-only ray tracing). Own `dump/` library. The toolchain and Python are read
  from the main checkout *by path* (`ATIV_WIN_TOOLCHAIN`, the `.venv` interpreter), never through a junction (the
  Uncharted copies once had an agent write into main through one).
- Firmware: copied the main checkout's decrypted 3.74 (`dump/firmware/3.74`) instead of re-decrypting the PUP.

## 1. Decrypt, import, analyze, recompile (minutes)

- `vitarecomp add app/PCSG00351 --no-build` (32 s, `work.bin` found by itself), then `add patch/PCSG00351`.
- The pack needs the SHA-256 of the 1.05 `eboot.bin.elf`; MODULES copied from Killzone's pattern (`libc libgxm_es4
  libgpu_es4 libscemp4 libsceavplayer`; the game's own libfios2/libult/libface/libsmart are shipped but not imported).
- 39,840 functions, 7.7 M instructions -> 1.1 GB of C (SPLIT = 100). Build ~6 min after a recompile, ~30 s after a
  runtime-only change.

## 2. Recompiler fixes found by the compiler

- Three parts failed with `goto L_x` without a label. Two causes, both fixed generally in `recompiler/recomp.py`:
  a function wrongly switched to ARM (its ARM decode had no instruction at the entry) and entries that fall *inside*
  an instruction (bogus pointer words). Only functions that failed to compile change.
- **Trap**: my own script `dev/psn_build_all.sh` ended with a failing `[ ]` test, so it exited 1 on success and the
  chained build never ran; the "same errors" I saw next were the OLD log. Now it ends with `exit 0`, and runs
  `dev/psnova/check_labels.py` (23 s) after every recompile so a 25-minute build can't fail on a missing label.

## 3. First boots: missed functions and a deadlock

- `RECOMP_IMPORTS=1` listed only 186 of 649 imports: the report scanned the main program only up to 0x82000000; this
  one is 20 MB. Fixed in `runtime/core/main.c`.
- First run stopped at `call to 0x8209d688: neither recompiled code nor an import`. It was an **ARM** method in a
  vtable of even (ARM) pointers; the run's miss log had written "thumb" (its rule follows the caller's mode, wrong for
  `blx` to an even address). Instead of re-running ~90 times, a scan of every even word that lands on uncovered code and
  decodes cleanly as ARM (`dev/psnova/even_pointers.py`) found 84 at once; the rule went into `analyze.py`
  (`arm_pointer_targets`, 92 found). The same scan proved no existing function was decoded in the wrong mode.
- The game then froze after frame 1. The call log (`RECOMP_LOG` through `run`, stdout/stderr -> session.log) showed a
  thread polling with `sceKernelDelayThread` and another waiting for bit 2 of an event flag that only a stubbed
  `sceKernelCancelEventFlag(flag, 2)` would set: the Aska engine starts every worker that way. Implemented in kernel.c.
  **Title screen reached.**

## 4. The button hunt (the longest part)

Symptom: input reached the game (`RECOMP_LOG_CTRL` showed `buttons 0x8`), nothing reacted, not even "skip movie".
What did NOT explain it (each checked): the save-slot stubs (that call only counts saves), sound not started, app
state (all zeros), and my own test setup skipping movies (it did cause a separate black-screen issue, see 5).

How it was found:
1. Only two controller call sites exist in the whole program (grep the generated C for `blx #<import stub>`):
   `fn_815920de` (every frame, but it keeps only L/R/L3/R3: the PS TV touch substitutes) and `fn_81b1c958`, the real pad.
2. `RECOMP_LOG_IMPORTS=sceCtrl`: the real pad was read **once**, at frame 0.
3. A native backtrace of that read (new `RECOMP_CTRL_BACKTRACE=1`, symbolised with `llvm-nm -n game_host.exe`; the
   recompiled functions are C functions, so the native stack is the guest's) gave the input thread's job loop
   `fn_81a1f276`: "while not quit: update 3 device slots; sleep 8 ms".
4. Pack trace hooks (`packs/PCSG00351/hooks.c`, `RECOMP_PSN_INPUT_TRACE=1`, an IHOOK on the slot load) showed the
   loop's object register r5 was 0 from the second pass on: a callee had smashed it.
5. The pad update's frame: sample at `sp+0`, canary at `sp+0x24`, saved r4-r8 from `sp+0x2c`. The runtime wrote each
   `SceCtrlData` as **64 bytes; it is 0x20**. The canary didn't catch it because `__stack_chk_guard` is left 0.
   Fixed in display.c: the pad update ran 218,000 times next run; Start, Cross, Circle all work.

Lesson: when a value turns 0 after a call, suspect a host function writing past a guest buffer; compare the game's
stack frame with the struct size the runtime writes.

## 5. Movies

- Sound played, the picture stayed black: no `sceAvcdecCreateDecoder` call. `RECOMP_LOG_IMPORTS=sceAvPlayer,sceAvcdec,
  sceVideodec,sceCodecEngine` showed `sceCodecEngineAllocMemoryFromUnmapMemBlock(.., 0x2c0000, align 0x100000) -> 0`:
  the game's block sat at 0x260b3000, and 1 MiB padding left too little room.
- Fix 1 (sysmem.c): blocks aligned by type as on the console (CDRAM 256 KiB, phycont 1 MiB). Fix 2 (video.c): the
  decoder size reported in whole MiB, so the AvPlayer's own carve fits (the second movie still failed without it).
- "Garbled subtitles" in the opening movie are SEGA's in-universe script: checked by decoding the same MP4 in the
  browser pane (local `http.server`; a blob URL to make it seekable; scan frames with a canvas for bright text).

## 6. Character creation crash (evening)

- The user's own windowed session (25 min) ended in character creation: `call to 0x822b0d6c: neither recompiled code
  nor an import`. Another ARM method, missed because my ARM rule also demanded an unconditional *second* instruction
  and this one starts `cmp r1, #0; beq`. The rule now rejects text by its bytes (all printable ASCII) and only needs the
  first instruction unconditional; a run-recorded "thumb" miss that is 4-aligned, stored as an even pointer and an ARM
  function is taken as ARM.

## 7. Character creation: loops in shaders, the name dialog, a recorder (evening)

- With the crash fixed, character creation ran at ~9 fps and its characters looked broken. The log said why:
  `gpu: 0x11107130: branch at instruction 62 (unconditional, offset -15) outside the structured forms translated`.
  Nativ's shader translator (`runtime/gfx/usse_spirv.c`) only translated predicated forward branches; its own comment
  said backward ones "aren't translated (none of the three games' programs seen so far use them)". Such a draw goes to
  the software renderer, which is slow and can't read this game's vertex positions.
- **Fix: a dispatcher** for programs the structured walk refuses: basic blocks cut at every branch and target, one SPIR-V
  loop (`OpLoopMerge`) around an `OpSwitch` on the next block's number held in a Private variable; a branch stores the
  taken / fall-through block. Registers and predicates already live in Private variables, so nothing else changes.
  A loop body that changes the translate-time register increments (SMLSI/SMBO) must leave them as it found them:
  checked by simulating them along the program (`moe_apply`). The first version refused any SMLSI after the loop's
  start, wrongly: the skinning program's SMLSI at instruction 130 is after its loop (47..62). Two opcodes had to be added
  to the translator's own list (OpLoopMerge 246, OpSwitch 251).
- **Fast loop for translator work**: one `vitarecomp capture` of a character-creation frame (9 min), then
  `build/gfxreplay.exe` re-translates its shaders in seconds (rebuild it with `dev/build_replay_win.sh` after a
  usse_spirv.c change). `RECOMP_REPLAY_DUMP=1` lists each draw's programs; `RECOMP_REPLAY_DRAWS=k` renders up to draw k:
  draws 9-28 (the looping program) render three properly skinned characters. The "broken" look in the full frame is the
  game's composition: they stand on an upper level behind a railing and the menu's depth effects.
- `sceImeDialog*` (the system keyboard, used to name the character) answers at once with the game's initial text, else
  `RECOMP_IME_TEXT`, else "Nova" (apputil.c). A real typing box in the overlay is a later task.
- **Gameplay recorder** (`RECOMP_VIDEO_DIR=<dir>`): gfx_gpu.c saves every presented frame as JPEG on two worker threads
  with its host time; display.c saves every audio buffer with its time, port and volume; `dev/psnova/make_video.py`
  mixes the audio onto the same clock and encodes H.264 + AAC with the ffmpeg already on this PC (Subtitle Edit's copy;
  Stremio has one too). No download was needed. gfxreplay needed stubs for the recorder's symbols.
- Windowed mode: `fullscreen = 0` in the game's own `recomp/settings.ini` (it overrides the shared settings file, which
  Claude's shell sees only as a redirected copy).

### No in-game sound -- found while making the video

- The first encoded clip had only movie sound. The logs of every run (and the user's 25-minute session) showed only
  movie audio ports, and the exit histogram showed `sceNgsSystemGetRequiredMemorySize` x7 and never
  `sceNgsSystemInit`. The game's CRI ADX2 checks the size right after asking (0x819d6804:
  `size + 0x10 > 0x2000 -> return -1`); the runtime answered 0x10000 (it keeps NGS state on the host and never uses that
  memory). Now 0x1000 (ngs.c): 11 NGS systems start, racks of 32 PCM / 16 ATRAC9 voices and mixer busses, the game's
  output port (256 samples at 48 kHz) stays open and carries the title music (`RECOMP_AUDIO_STATS=1`: rms 1,500-3,700).
- Lesson: "sound unverified by ear" hid a total failure for a whole day. Check the audio ports and their levels in the
  first runs of a new game, not when someone listens.
- The fix woke code that had never run: the first run with it stopped at the title on `unimplemented instruction at
  0x819f5716` = `vqmovn.s32 d16, q8` (CRI's mixer: float mix -> `vcvt.s32.f32 #15` -> saturating narrow to 16-bit
  PCM). The recompiler had no `vqmovn`, `vzip` or q-register `vshr.u64`; all three added (recomp.py, beside `vmovn`
  and `vuzp`; `vqmovn` sets FPSCR.QC like the hardware). A grep of the generated C for `UNIMPL(c, 0x` grouped by
  mnemonic lists what is left: only `vseleq.f64` (ARMv8, cannot run on the Vita's Cortex-A9: data decoded as code) and
  `bkpt`. Do that grep after every recompile of a new game, before the first run, not after a stop.

### The abort after "Start the Game"

- The margin-based script got through the whole creation (name typed through SceIme) and pressed Yes on "will be
  saved"; the game then called `abort()` (`sceKernelCallAbortHandler` from libc, lr 0x8802ad2b) ~1,000 frames later.
  The abort handler now prints the native backtrace (the guest chain).
- The chain (llvm-nm on game_dev.exe): libc abort <- `std::_Xlength_error("map/set<T> too long")` <- fn_81b2a8bc, an
  MS-STL tree insert (`size >= 0x071c71c6` = max_size of 36-byte nodes; the game's `Framework/STL_Map.h` with its own
  allocator) <- fn_81b3b780 (a `map<thread id, ...>`: keys compared by `_Thrd_lt`) <- **fn_815cf88c** <- fn_81b4db10
  (a pointer-to-member call `{ptr, adj, object}`) <- fn_815b32fe (a message handler) <- ... <- an Aska worker thread.
  No save-data call happens between Yes and the abort.
- A hook on the insert (pack HOOKS, hooks.c `psn_tree_insert`) showed the "tree" is 0x815cf8e3: a Thumb code address.
  fn_815cf88c is **not a function**: 0x815cf88c is the middle of a loop in fn_815cf358, and the analysis made it an
  entry because the bytes of the instruction `strb.w r8, [sp, #0x15c]` (`8d f8 5c 81`) read as the word 0x815cf88d,
  a "Thumb code pointer" (same for 0x815cf8c6/8c8/8da/8dc). Such false entries are harmless while nothing calls them;
  here the game itself called 0x815cf88d through the member-pointer call (`recomp_lookup` is an exact switch), so the
  functor or its object was wrong before the call. One way that reads instruction bytes: a virtual member call whose
  object pointer is wrong, so its "vtable" points into code. Next hook: `psn_member_call` (the functor, object,
  vtable, the caller's message and the last 64 calls).
- That hook never fired: the native frames named fn_81b4db10/fn_81b31ae0 (identical 79-line thunks) are not to be
  trusted (identical code, folded or misnamed). **The real cause was in the code itself.** fn_815cf358 has a hole at
  0x815cf8dc-0x815cf8df: the analysis made 0x815cf8dc a 4-byte function of its own (another strb.w read as a pointer),
  so the two branches there (`cbnz r0, 0x815cf8dc`, `bne 0x815cf8dc`) compiled as tail calls into fn_815cf8dc -- and
  recomp.py emitted tail calls through `call()`, which **sets lr** to the branch's next address. That code keeps a
  tree node in lr (`ldr.w lr, [r8, #4]`, a register-starved loop) and the instruction at 0x815cf8dc is `mov r8, lr`:
  r8 = 0x815cf8b7, then `add.w r4, r8, #0x2c` = **0x815cf8e3**, the exact "tree" the hook saw. An ARM `b` never writes
  lr. Fix (recomp.py `tail()`): b/cbz into another function leaves lr alone (computed jumps already did); only bl/blx
  set it. False entries stay (they run the same code with the same registers now); filtering Thumb words that are
  instruction bytes out of the pointer scan would remove them, at the risk of missing a real pointer.
- Lesson: when a pointer is a code address, compute backwards from the instructions just before it (here `r8 + 0x2c`)
  before hooking further out; and a native backtrace through small identical thunks can name the wrong function.
- Same rebuild: the Luufen fork's dfc075d (`vld1/vst1 {..}, [rN], rM` never advanced rN; Nova's CRI mixer stores
  8 rows that way at 0x819fbea4), from the Uncharted session's fork comparison.
- Result (test43, then the recording take4): no abort. The save dialog saves (569,108 bytes, slot 0), then the warp
  cutscene, the ship corridor, Rietheia's and Filldia's dialogue, and the **training arena with its HUD** (HP 251/251,
  "Move to the arrows!") by frame ~22,000; the take ran to 29,000 with 20,352 frames recorded, 0 dropped. The save is
  kept in `dump/saves/after-creation-2026-11-18/` (the test folder's fs is rebuilt every run).

  every page the game touched since whose bytes changed (raw path: download to a host buffer, copy around the kept
  pages; float path: save/restore around the CPU encode only); the target re-uploads before its next GPU use.
  `RECOMP_GPU_NO_KEEP_REWRITTEN=1` turns it off.

## Techniques worth reusing

| Need | How |
|---|---|
| Which imports a game needs | `RECOMP_IMPORTS=1 RECOMP_HEADLESS=1 vitarecomp run <title>` |
| A cheap call log of chosen imports | `EXTRA_ENV="RECOMP_LOG_IMPORTS=name1,name2"` (full `RECOMP_LOG` is far too slow here: 4 M calls before frame 3) |
| Every thread's last call | a run that ends (bad call, or a call budget: `run <title> <calls>`) prints them |
| Who calls an import | grep the generated C for `blx #0x<stub>` (stub addresses: `recomp_import_name` in game.c) |
| The guest call chain at a moment | a native backtrace + `llvm-nm -n game_host.exe` (ImageBase 0x140000000) |
| Watching a register or object | a pack HOOK/IHOOK in `packs/<title>/hooks.c` (needs recompile + build) |
| Screenshots of a scripted run | `TEST_INPUT=... SHOT_EVERY=100 TEST_FRAMES=n EXTRA_ENV="RECOMP_GFX=gpu RECOMP_CLOCK=real" vitarecomp test`; `dev/ppm2png.py` |
| A frame's draws | `vitarecomp capture` + `build/gfxreplay.exe` with `RECOMP_REPLAY_DUMP=1` (build it with `dev/build_replay_win.sh`) |
| Instructions the recompiler left out | `grep -h -B2 "UNIMPL(c, 0x" recomp/game_part*.c \| grep "^L_"`, counted by mnemonic (run after each recompile) |

## Traps (do not repeat)

- `vitarecomp test` sends the game's stdout to nowhere: call logs need `run` (headless) and `RECOMP_LOG` set in the
  pipeline's own environment (run pins it from there), not in `EXTRA_ENV`.
- `RECOMP_LOG_FROM_FRAME` printed nothing here (cause not looked into); `RECOMP_LOG_FROM=<call>` works.
- The software renderer can't replay this game (`no position attribute`: its vertex inputs are named `vsin.vPos`), so
  a soft/GPU replay comparison proves nothing here.
- The test settings once skipped movies (`RECOMP_SKIP_MOVIES=1`): the AvPlayer then answers "no stream"; don't judge
  movie or title behaviour from such runs.
- `__stack_chk_guard` is 0 in Nativ: canaries never fire, so stack overflows from host code are silent.
- The permission check refuses killing the user's game process; ask the user to close it.
- The worktree's path has spaces: quote every `$W/...` in shell commands. An unquoted `cp -al $W/a $W/b` split into
  words and an `&&` chain silently skipped the test it was meant to set up.
- Bash heredocs here collapse `\\` (a Python string with `\N` broke): write such scripts with the Write tool.
- The recording's `frames.txt` numbers frames from 1 across the recorded ranges, not by game frame (game frame g in
  the second range is index g - first range start + first range length...: 8,648 for ranges 1450-2300,9500-...).
